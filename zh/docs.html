概述

MPE Flow 是一款高性能跨协议工作流编排与执行引擎。通过单一可执行文件，即可无缝运行桌面端图形界面 (GUI) 或独立无头命令行工具 (CLI)。

单二进制，双运行模式

  • 无启动参数 → 启动 Tauri 桌面端图形化界面
  • 携带命令行参数 → 进入无头高并发 CLI 执行模式

在 Linux 平台上，提供轻量纯 CLI 二进制，无需任何 GTK/WebKit 等图形库依赖。

安装指南

Windows

前往 更新日志 页面下载 Windows 平台安装包（.exe 安装程序或免安装版），双击即可完成安装。

macOS

前往 更新日志 页面下载 macOS 的 Universal DMG 镜像包（单个安装包已同时原生适配 Apple Silicon M 系列芯片与 Intel 芯片机型）。双击打开 DMG 文件后，将 MPE 图标拖入 Applications（应用程序） 文件夹即可。

macOS 首次打开提示“无法验证开发者”或“已损坏”解决办法

原因告知：由于当前项目为开源阶段，发布版本尚未购买并配置昂贵的 Apple 商业开发者证书公证（Apple Notarization）。macOS 系统的 Gatekeeper 安全机制在首次运行未签名应用时，会拦截并弹出安全警示：“无法打开 MPE，因为 Apple 无法检查其是否包含恶意软件” 或 “MPE 已损坏，您应该将它移到废纸篓”。这是 macOS 对未签名软件的默认安全拦截策略，软件源码完全公开、无毒安全，请放心使用。

遇到拦截提示时，只需通过以下任一方式解除隔离，后续即可正常双击启动：

方式一：终端命令一键解除隔离属性（推荐，彻底解决“损坏”提示）

将 MPE 拖入“应用程序”文件夹后，打开系统自带的“终端 (Terminal)”，粘贴并执行以下命令：

xattr -cr /Applications/MPE.app

执行完成后，再次在“启动台”或“访达”中直接双击 MPE.app 即可直接运行，此后系统将永久信任并正常打开。

方式二：通过访达右键强制打开

  1. 打开访达 (Finder)，进入应用程序 (Applications) 目录找到 MPE 图标。
  2. 按住键盘上的 Control 键不放，同时使用鼠标右键点击（或触控板双指轻点）MPE 图标，在弹出的上下文菜单中点击“打开 (Open)”。
  3. 在随后弹出的系统对话框中，系统会提供额外的“打开”按钮，点击该按钮即可正常启动。（仅需首次操作一次，之后双击即可直接运行）。

Linux (纯 CLI)

下载预编译二进制并加入系统 PATH：

# 下载并解压
curl -LO https://download.mpe.run/releases/latest/mpe-vX.Y.Z-linux-x86_64.tar.gz
tar xzf mpe-vX.Y.Z-linux-x86_64.tar.gz

# 赋予执行权限并移入 PATH
chmod +x mpe
sudo mv mpe /usr/local/bin/

# 验证安装
mpe --help

说明

Linux 版本为纯 CLI 模式，轻量零 GUI 依赖，非常适合 Docker 容器与 CI/CD 宿主机环境。

快速示例

创建一个工作流文件 hello.mpf（默认采用简洁直观的 YAML 格式）：

_version: 1
flow:
  uuid: example-flow
  name: Hello World
  nodes:
    - uuid: entry-1
      type: entry
      name: Start
      data:
        type: entry
    - uuid: http-1
      type: http:request
      name: Fetch Data
      data:
        type: http:request
        url: https://httpbin.org/get
        method: get
    - uuid: end-1
      type: end
      name: End
      data:
        type: end
  connections:
    - id: conn-1
      source_node_uuid: entry-1
      target_node_uuid: http-1
      source_port_id: out
      target_port_id: in
    - id: conn-2
      source_node_uuid: http-1
      target_node_uuid: end-1
      source_port_id: "true"
      target_port_id: in

运行工作流：

mpe run -f hello.mpf

默认 YAML 格式与全量 JSON 兼容

自 v0.3.0 起，MPE 流程文件（.mpf）默认采用 YAML 格式存储，带来清晰的 Git 差异与多行脚本编写体验。底层引擎、CLI、桌面端与在线 Playground 均原生自适应解析 YAML 与历史 JSON 格式。您可以通过 mpe flow fmt 随时在两种格式间转换或格式化。

全域 AI 助手与智能编排

MPE Flow 原生内置了深度集成的全域 AI 流程编排架构师（Agentic AI Copilot），具备自然语言工作流生成、自主推进「执行到底」、自适应折行排版优化与一键报错智能自愈等全套智能体能力。

隐私优先与数据主权

内置 AI 助手支持连接任意兼容 OpenAI 协议的大模型服务（包括 DeepSeek、OpenAI、Claude、Kimi、通义千问等，或通过 Ollama / vLLM 本地离线私有化部署的模型）。所有工作流、Token 和测试数据完全留存在本地设备，无强制云端同步或账户锁定。

配置 AI Provider

前往系统设置 全局设置 → AI 助手 即可添加与管理模型服务商：

  • 常用服务预设： 提供 DeepSeek、OpenAI、Claude、Kimi、Ollama 等主流厂商的常用预设，一键填入 Base URL 与推荐模型。
  • Base URL 与 API Key： 自由接入公有云 API 或本地自建大模型端点（例如本地 Ollama 服务 http://localhost:11434/v1）。
  • 模型自省与选择： 支持一键拉取服务商模型列表，或手动指定任意模型标识（如 deepseek-chat、deepseek-reasoner、gpt-4o、claude-3-5-sonnet）。
  • 自定义全局 System Prompt： 注入您团队的特定业务规范、接口命名偏好或统一脚本风格，每次对话时自动附加生效。

交互形态与全局快捷键

MPE Flow 提供了四种无缝衔接的 AI 助手交互入口：

交互形态 快捷键 / 触发方式 功能说明
右侧 Copilot 侧边栏 Ctrl+I / Cmd+I 内置多会话管理、历史记录持久化、模型实时切换与上下文感知对话。
脱离吸附 (浮动窗口) 按住顶部拖拽 / 点击脱离按钮 将 Copilot 变为独立可拖拽移动的浮动窗口，适合多显示器编程。拖回右侧边缘即可一键重新吸附。
Spotlight 快捷指令 Ctrl+K / Cmd+K 居中唤起全局指令弹窗，无需展开侧边栏即可通过自然语言一键生成流程、排版或调试。
CLI AI 双向桥接 mpe ai "<指令>" 在终端直接向 AI 助手下发指令，自动联动正在运行的 GUI 界面或在无头模式下执行。

画布操作与自然语言流程生成

AI Copilot 不仅能回答文本，更通过强类型 Tool Calling 直接操控图形化画布：

  • 自然语言生成 DAG： 例如：“创建一个登录认证并提取 Token 传递给下游 WebSocket 长连接的完整工作流”。
  • 批量编排流水线： 具备 batch_create_pipeline 能力，一条指令即可原子化创建多节点复合流转拓扑并自动建立端口连线。
  • 自动排版与自适应折行： 支持传统水平/垂直 DAG 排版，并全新引入 自适应折行布局算法 (Adaptive Wrap)，自动根据视口与多分支层级优化排版，杜绝连线重叠与无限横向拉伸。
  • 脚本生成与修复： 自动编写满足 QuickJS / Rhai 运行时规范的 JavaScript 脚本，完成复杂加解密、动态计算与数据清洗。
  • 数据源检索与导入： 感知已接入的 OpenAPI / Swagger 规范，按需自动导入接口并转为工作流节点。

自主推进模式（执行到底）与中途纠偏插话

面向复杂的多步验证与探索性编排场景：

  • 执行到底模式 (Auto-Execute)： 开启后 AI 将自主连续调用工具、执行节点并观察产物，直到达到既定业务目标或通过全部断言。
  • 中途纠偏插话 (Midway Steering)： 当 AI 正在批量执行或持续推理时，无需中止任务，可直接在输入框发送补充指令（例如：“端口改用 8080”），AI 将实时吸收新指令动态微调后续步骤。
  • 思考链透明化 (Thinking Chain)： 原生适配 DeepSeek-R1 等推理模型，流式解析 <think> 标签，提供可折叠展开的推理思考过程展示。
  • 高风险操作安全确认： 清空画布、批量删除节点、安装外部插件等破坏性操作前，弹出用户确认卡片，需人工授权后方可执行。

节点报错一键 AI 深度诊断与自愈

当协议节点执行遇到异常（HTTP 500、WebSocket 握手超时、断言失败等）：

  • 在错误提示条或执行历史面板中点击 AI 诊断与修复。
  • Copilot 自动采集上游节点上下文、出入参快照与底层错误链进行归因分析。
  • 清晰呈现根因（如认证头缺失、Token 失效、JSONPath 语法错误），并在画布中一键应用推荐修复方案。

本地工作区代码感知与多模态

点击 关联本地项目，将工作流与本地源码工程建立连接：

  • 项目结构扫描： 自动感知工程技术栈、路由文件、OpenAPI 文档与配置文件。
  • 切片阅读与代码检索： 检索后端 Controller、DTO 定义与环境变量规范，精准填充接口路径与请求体格式。
  • 截图多模态输入： 支持直接粘贴或拖拽接口文档截图、错误弹窗截图，AI 自动结合图像信息完成配置。

快捷斜杠指令与人机交互工具

MPE Flow 为全域 AI 助手配备了高频键盘快捷指令与人机协同工具桥接：

  • 斜杠快捷指令 (/)： 在聊天输入框中输入 / 即可呼出自动补全悬浮面板：
    • /fix — 一键深度诊断并修复当前选中节点或最近失败节点的配置报错。
    • /explain — 剖析当前激活工作流的拓扑结构、变量流转与业务链路。
    • /test — 根据上游协议返回的数据特征，智能生成断言节点与边界用例。
  • 交互式问询卡片 (ask_user)： 当大模型需要用户决策（如选取鉴权范围、确认环境地址、选择替代分支方案）时，自动生成交互式单选/多选或表单卡片，并安全挂起工具执行循环，等待用户点击提交后继续推进。
  • 安全白名单终端工具 (terminal_exec)： AI 可在关联的工作区中执行经白名单严格校验的系统命令（如 git status、npm test、cargo check），高危操作强制触发卡片二次确认。
  • 全信任自主模式 (Full Trust Mode)： 资深开发者可在设置中启用全信任模式，自主推进执行时免除频繁手动卡片点击，实现全自动端到端探索。
  • 思考水滴物理动效与 Token 统计： 深度思考模型推理时，实时显示字数统计与下落堆叠水滴加载动画，推理链路直观生动。

CI/CD 集成 (GitHub Actions)

mpe run 支持将执行结果导出为标准 JUnit XML 格式，可直接被 Jenkins、GitHub Actions 和 GitLab CI 等持续集成平台识别与解析。工作流中的每个节点对应一个 <testcase>；执行失败和跳过的节点分别映射为 <failure> 和 <skipped> 元素。

# 导出指定 staging 环境的 JUnit XML 报告供 CI 使用
mpe run -f flow.mpf -e staging --report-format junit --report-file results.xml
# 或者直接将 JUnit XML 输出到 stdout（不带 --report-file）
mpe run -f flow.mpf --report-format junit

在仓库中添加工作流步骤，通过 dorny/test-reporter 在 Pull Request 中自动执行工作流并展示测试报告：

name: Flow Tests

on:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run MPE flows
        run: |
          mpe run -f tests/flows/api-smoke.mpf --report-format junit --report-file results.xml

      - name: Publish test report
        if: always()
        uses: dorny/test-reporter@v1
        with:
          name: MPE Flow Results
          path: results.xml
          reporter: java-junit
          fail-on-error: 'true'

提示

JUnit 报告如实反映节点级别的测试结果：断言、HTTP、WebSocket 等协议节点映射为独立的测试用例。任何节点执行失败都会导致非零退出码，因此 mpe run --report-format junit --report-file results.xml 默认会在失败时使 CI Job 报错中断。

工作流文件格式规范 (.mpf)

MPE 流程文件采用 .mpf 扩展名，遵循 FlowFile 统一包装格式。流程文件默认采用 YAML 格式持久化（同时保持对历史 JSON 文件的无缝向下兼容）：

_version: 1
flow:
  uuid: my-flow
  name: My Flow
  initial_variables:
    api_base: https://api.example.com
    token: abc123
  nodes:
    # 节点列表数组 ...
  connections:
    # 连线列表数组 ...

Top-level Fields

Field Type Required Description
_version number No File format version (default: 1)
flow object Yes Flow data container

Flow Fields

Field Type Required Description
uuid string Yes Unique flow identifier
name string Yes Human-readable flow name
initial_variables object No 工作流自身内置的兜底变量（通过 {{key}} 插值）。作为四级级联解析中的兜底层。
nodes array Yes 属于 Main 业务核心阶段的节点列表
connections array Yes Main 阶段节点之间的有向连线集合
setup object No 可选的 FlowSubGraph 子图（{ nodes: [], connections: [] }），在测试前单次执行，导出的变量直接注入 Main 阶段。
teardown object No 可选的 FlowSubGraph 子图，在测试后单次执行（用于告警通知与清理），注入只读保留变量 $report。

环境定义解耦存储说明

环境变量集已不再内嵌保存在 .mpf 流程文件中，而是作为独立的 YAML 文件存储在 <flows_dir>/environments/ 目录下（如 dev.yaml、staging.yaml、prod.yaml），支持跨所有流程全局共享。历史旧流程文件中内嵌的环境配置在加载时会自动忽略，请通过环境管理器或 mpe env 命令重新创建。

节点配置结构 (Node)

uuid: node-uuid
type: http:request
name: My HTTP Request
data:
  type: http:request
  url: https://api.example.com
  method: get
Field Type Required Description
uuid string Yes Unique node identifier
type string Yes Node type (e.g. http, entry)
name string Yes Display name
data object Yes Node configuration. Must include "type" matching the node type
on_error string No Error strategy: "route_to_false" (default), "ignore", "abort_flow"

重要规则：data.type 字段

每个节点的 data 对象内部必须显式包含 "type": "<node_type>" 以便 Rust 核心引擎正确反序列化，其取值必须与节点顶层的 type 字段完全保持一致。

节点连线规范 (Connections)

连线定义了工作流节点之间的有向执行流向与数据传递拓扑。

id: conn-1
source_node_uuid: entry-1
target_node_uuid: http-1
source_port_id: out
target_port_id: in
字段 说明
source_node_uuid 源节点的 UUID
target_node_uuid 目标节点的 UUID
source_port_id 源节点输出端口：out（单输出端口）、true/false（双分支端口）
target_port_id 所有节点的输入端口统一必须为 "in"

关键端口连线约束

  • 所有节点的 target_port_id 必须是 "in"（而非 "input"）
  • 具备双输出端口（true/false）的节点，建议同时连接两条分支连线，避免某分支无连线导致意外终止流程
  • entry 只有 out 输出端口，end 只有 in 输入端口无输出端口

变量系统

变量池 (Variable Pool) 与节点输出的关系

{{var}} 插值语法只能读取工作流变量池中的变量。协议节点的直接输出独立缓存在 last_node_output 中，默认不会自动写入变量池。

如需在后续节点中通过 {{var}} 引用上一步的输出数据，请先通过 variable:extractor 变量提取节点或 script 脚本节点提取到变量池。

语法规范

插值语法 说明
{{variable_name}} 引用变量池中的指定变量
{{obj.field}} 通过点号语法访问嵌套 JSON 对象的内部字段

向变量池注入变量

  1. 初始化变量：在工作流全局设置 flow.initial_variables 中定义
  2. 变量提取节点：使用 variable:extractor 配合 JSONPath 从 last_node_output 提取
  3. 脚本注入：在 script 节点中使用 fn.variables.set(name, value)
// variable:extractor example
{
  "type": "variable:extractor",
  "data": {
    "type": "variable:extractor",
    "output_mappings": [
      { "source": "$.body.id", "target": "user_id" },
      { "source": "$.status", "target": "http_status" }
    ]
  }
}

// Later use: {{user_id}}, {{http_status}}

内置动态变量 (Dynamic Variables)

MPE Flow 深度内置了一系列免声明的动态变量，在每个步骤执行时实时计算取值：

动态变量 说明 取值示例
{{$timestamp}} 当前 Unix 毫秒时间戳 1772867200123
{{$isoTimestamp}} ISO 8601 UTC 格式当前标准时间 2026-09-07T12:00:00.000Z
{{$guid}} / {{$uuid}} 随机生成的 UUID v4 唯一标识 a3f89021-4b12-42fe-b58f-287517c2f829
{{$randomInt}} 随机 6 位正整数 (0-999999) 482103
{{$randomAlphaNumeric}} 随机 8 位大小写字母与数字组合字符串 k9X2mQ8L

Conditional / Assertion Paths

conditional and assertion nodes read directly from last_node_output:

Node Path Format Example
conditional.field_path Plain name, {{var}}, or $.path status, $.body.id
assertion.target JSONPath with $. prefix (required) $.status, $.body.data.id

语法约束

  • 仅支持对象点号属性访问：{{obj.field.subfield}}
  • 暂不支持数组下标索引：{{items[0]}}
  • 暂不支持行内函数调用：{{func()}}

全局环境与机密安全分层

MPE Flow 将环境配置从工作流文件中彻底解耦。环境定义作为独立的 YAML 文件存储在 <flows_dir>/environments/ 目录下（默认位于 ~/.app/flows/environments/，亦可通过 MPE_ENVIRONMENTS_DIR 环境变量覆盖），支持在所有工作流之间全局复用 dev、staging、prod 等多套环境变量集。

双文件机密隔离架构

每个环境均支持双文件设计，天然兼顾团队协同共享与个人本地敏感机密隔离：

  • 共享基础文件（<name>.yaml）： 存储团队通用配置（如服务域名、公共端口、公共超时策略等），直接随工作流一同提交入库 Git。
  • 机器私有覆盖层（<name>.local.yaml）： 在本地机器上无缝覆盖共享文件中的同名变量，专用于存放开发者个人 API Token、数据库密码与私钥。建议在 .gitignore 中添加 *.local.yaml，彻底杜绝机密误入代码仓库。
# <flows_dir>/environments/staging.yaml（团队共享，提交入库 Git）
name: staging
description: 测试环境配置
variables:
  API_URL: https://staging-api.example.com
  TIMEOUT_MS: 5000
  MOCK_MODE: false

# <flows_dir>/environments/staging.local.yaml（个人本地私有，加入 .gitignore）
name: staging
variables:
  AUTH_TOKEN: dev_secret_bearer_token_xyz987
  CLIENT_SECRET: sk_staging_99214a8f

四级变量解析级联优先级

在单次执行、单步调试或并发压测工作流时，变量将严格按照以下四级优先级进行级联解析与合并：

优先级 变量层级 作用域与来源 典型应用场景
1 (最低) 流程兜底变量 (Flow Fallback) .mpf 流程内的 flow.initial_variables 工作流自身内置的缺省变量，保证脱离全局环境时流程依然可自包含运行。
2 共享环境文件 环境目录下的 <name>.yaml 团队共享的全局环境地址、公共超时阈值与通用开关配置。
3 本地私有覆盖 环境目录下的 <name>.local.yaml 当前开发机私有的密码、测试账号凭据或本地代理配置。
4 (最高) 运行时参数覆盖 CLI --var KEY=VALUE 或运行入参 CI/CD 动态临时注入的构建流水线号、单次测试参数或运行时环境变量。

变量插值语法规范

级联合并后的变量统一通过裸键语法读取：{{API_URL}} 或嵌套字段 {{USER.id}}。请勿添加 env. 前缀（如 {{env.API_URL}} 属于无效语法，引擎将提示找不到该变量）。

GUI 桌面端环境交互

  • 左侧面板环境折叠区： 侧边栏支持按需展开/收起环境列表，支持显示各环境变量数量角标，并可一键完成环境激活、重命名、复制副本与删除。
  • 画布顶部工具栏选择器： 在画布顶部快速切换当前激活环境，即时生效，无需退出画布。
  • 环境管理器弹窗（双模式）：
    • 全局模式： 支持带语法高亮与校验的 YAML 直读直写编辑，独立切换查看与编辑共享层及本地私有覆盖层。
    • 画布模式： 并排展示当前流程的兜底变量，并通过级联对比矩阵 (Cascade Comparison Matrix) 直观对比各层取值与最终生效值。
  • 全执行链路贯通： 交互式运行、单步断点调试（F10/F11）与高并发压测均会自动带入并合并当前激活环境。
  • 流程导出环境烘焙与敏感凭证扫描： 导出工作流时可选择将当前激活环境的变量直接“烘焙”写入 flow.initial_variables，生成自包含的单文件。内置凭据安全扫描，自动检测 key、secret、token、password、auth、cred、cert、private 等敏感关键字并提示清除，避免密钥外泄。

环境存储目录配置

环境目录默认跟随流程目录派生（<flows_dir>/environments），支持通过以下方式灵活自定义：

  • GUI 设置： 设置 (Settings) → 存储 (Storage) → 环境文件目录 (environmentsDir)。
  • 环境变量： 设置 MPE_ENVIRONMENTS_DIR=/path/to/environments。
  • 配置文件： 在 config.toml（位于 $MPE_CONFIG 或系统数据目录）中设置 storage.environments_dir。

CLI 环境管理 (mpe env)

在无头 CI/CD 服务器或脚本中，可直接通过 mpe env 子命令全功能管理环境文件：

# 列出所有环境（名称、变量数、是否存在本地私有覆盖、文件路径）
mpe env list --format table

# 查看指定环境变量（支持查看 merged 合并层、base 共享层或 local 本地层）
mpe env show staging --source merged
mpe env show staging --source base
mpe env show staging --source local

# 向团队共享环境写入变量
mpe env set staging API_URL=https://staging.example.com TIMEOUT_MS=6000

# 向本地私有覆盖层写入敏感机密（保存至 .local.yaml）
mpe env set staging AUTH_TOKEN=secret_token_12345 --local

# 删除指定环境的本地覆盖层或完整删除环境
mpe env delete staging --local
mpe env delete staging

指定环境执行工作流

在 mpe run、mpe debug 或 mpe stress run 中通过 -e, --env <NAME> 指定环境：

# 指定 staging 环境执行流程
mpe run -f flows/checkout.mpf -e staging

# 指定环境并附加运行时变量临时覆盖
mpe run -f flows/checkout.mpf -e staging --var TIMEOUT_MS=10000 --var NOTIFY=true

# 指定 staging 环境进行压力测试
mpe stress run -f flows/checkout.mpf -e staging -u 100 -r 15

流程生命周期阶段 (Setup / Main / Teardown)

MPE Flow 将工作流执行模型升级为原生的一等公民生命周期三阶段架构。告别了脆弱、难以排查的回调函数机制，每个阶段均是完整的可视化多协议画布子图，无缝兼容所有协议节点：

传统 Hook 机制已全面替换为 Teardown 阶段

在 0.5.0-beta 版本中，传统的流程 Hook 机制（EntryConfig.hooks）已被彻底移除。取而代之的是功能强大、可视化可编排的 Teardown 后置阶段。支持在测试结束后使用真实的协议节点（HTTP、脚本、断言、数据库操作）执行告警与清理，具备完整的连线路由、变量插值与断点调试能力。

三大阶段职责分工

阶段名称 对应字段 执行频次与场景 核心职责与变量流转
Setup (前置预热) flow.setup 运行前单次执行 登录认证预热、Token 获取、测试数据集初始化与测试环境预校验。Setup 节点中导出的所有变量会自动合并注入 Main 业务阶段的变量上下文。
Main (核心业务) flow.nodes / flow.connections 单次运行 / 压测并发循环 / 数据集逐行消费 被测试的核心业务拓扑图。在阶梯高并发压测 (mpe stress run) 时，仅在各虚拟用户间并发循环 Main 阶段节点，Setup 与 Teardown 仅在加压前后单次执行，确保 QPS/P99 指标纯净。
Teardown (后置清理) flow.teardown 运行后单次执行（无论成败） 飞书/企业微信/Slack/邮件告警推送、临时脏数据与测试会话清理。继承 Main 阶段所有变量，并注入只读保留变量 $report。

Teardown 阶段中的只读 $report 报告变量

Teardown 阶段在启动时会自动注入代表 Main 核心业务执行结果的保留变量 $report，可在节点配置或脚本中直接读取：

  • {{$report.status}} — Main 阶段执行状态（"success"、"failed"、"cancelled"）。
  • {{$report.duration_ms}} — 核心业务流程的实际执行耗时（毫秒）。
  • {{$report.node_reports}} — 各节点执行明细、输出数据、状态码与断言判定结果列表。
# 示例：在 Teardown 的 HTTP 节点中向群机器人发送自动化测试汇总卡片
{
  "msg_type": "text",
  "content": {
    "text": "【API 自动化测试报告】状态: {{$report.status}}, 核心链路耗时: {{$report.duration_ms}}ms"
  }
}

阶段失败与容错传播规则

  • Setup 阶段失败： 若 Setup 中任一节点遇到未捕获异常或路由至 false 端口，系统将跳过 Main 阶段（标记为 stages.main.status == "skipped"），但依然会执行 Teardown 阶段清理已申请的前置资源。
  • Teardown 阶段失败： 若 Main 业务已顺利通过但 Teardown 阶段清理失败，整体流程标记为失败，但报告中 stages.main.status 保持 "success" — 严格区分业务功能正确性与基础设施清理偶发故障。
  • 无依赖根节点确定性执行： 在 Setup 和 Teardown 子图中，若存在多个无前驱连线的根节点（入度为 0），执行引擎将严格依据画布上的 (y, x) 坐标自上而下、从左向右确定性执行，彻底杜绝 JSON 数组乱序执行隐患。

画布阶段切换胶囊栏 (StageTabBar)

画布左上方常驻紧凑的阶段切换胶囊栏（Setup | Main | Teardown），悬停即可查看各阶段说明。添加、连线、删除节点以及撤销/重做操作均严格隔离在当前活跃阶段内。

开始与结束节点 (Entry / End)

Entry 开始节点

工作流各阶段的起始触发点，单图画布中必须且只能存在一个有效 Entry 节点（支持画布调色板便捷添加，具备防重复唯一性保护）。

{
  "uuid": "entry-1",
  "type": "entry",
  "name": "开始",
  "data": { "type": "entry" }
}

End 结束节点

工作流终端节点。当执行流推进至 end 节点时，当前阶段正常终止。

{
  "uuid": "end-1",
  "type": "end",
  "name": "结束",
  "data": { "type": "end" }
}

子流程节点 (Subflow)

子流程节点支持将其他独立工作流（.mpf 文件或工作区已存流程）作为模块化子节点嵌入到当前流程中，实现高内聚、可复用的复杂业务流编排。

画布拖拽生成与标签联动

支持直接从左侧侧边栏流程列表拖拽任意流程文件到画布中央，系统将自动创建并绑定该流程的子流程节点。双击子流程节点或在配置面板中点击“打开流程”，将在顶部多标签栏 (FlowTabBar) 中以独立标签打开目标子流程，便于即时查看与编辑，同时保留当前父流程的草稿与调试状态。

{
  "uuid": "subflow-1",
  "type": "flow:sub",
  "name": "用户登录与鉴权子流程",
  "data": {
    "type": "flow:sub",
    "target_flow_id": "7b6c3d9a-1234-5678-abcd-ef0123456789",
    "target_flow_path": "./subflows/auth.mpf",
    "inherit_all_variables": true,
    "variable_mappings": [
      { "source": "parent_username", "target": "login_user" },
      { "source": "parent_password", "target": "login_pass" }
    ],
    "export_all_variables": true,
    "output_mappings": [
      { "source": "access_token", "target": "auth_token" }
    ]
  }
}

配置参数详解

参数字段 类型 默认值 说明
target_flow_idstring (可选)null工作区中已保存流程的 UUID（桌面端 GUI 模式下引用）。
target_flow_pathstring (可选)null目标 .mpf、.yaml 或 .json 流程文件的相对或绝对路径（跨环境迁移与 CLI 模式引用）。
inherit_all_variablesbooleantrue是否自动将父流程上下文中的所有变量继承给子流程。
variable_mappingsarray[]显式入参映射规则（source 父变量名/表达式 → target 子流程变量名），优先级高于自动继承。
export_all_variablesbooleantrue子流程执行完毕后，是否将子流程产生的所有变量自动回传合并至父流程变量池。
output_mappingsarray[]显式出参回传规则（source 子流程变量名 → target 父流程变量名），用于精准控制回传命名。

导出变量静态推断与预期预览

MPE Flow 内置静态代码与变量流转推断分析引擎。配置面板能够深度解析目标子流程结构，预先推断出其内部提取并导出的变量清单（如 variable:extractor 或 script 导出的变量），在子流程面板中直接呈现「预期导出变量预览」，支持一键复制变量名，并在下游节点引用时智能弱化未声明告警提示。

环路依赖检测与防死锁

MPE Flow 的 DAG 编译器在预检阶段即对子流程依赖图执行拓扑排序与环路检测。若存在直接自引用（A → A）或相互间接循环调用（A → B → A），校验器将立即拦截并给出明确的环路路径报错，彻底防止无限递归死锁。

树状嵌套执行报告

子流程执行完毕后，其内部所有节点的执行耗时、状态、输入输出及断言指标均完整保存在层级化的执行报告树中，可在执行历史面板中层层展开深入溯源。

HTTP 请求节点 (http:request)

发送高吞吐 HTTP/HTTPS 网络请求，支持 GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS 等全套标准方法。

{
  "uuid": "http-1",
  "type": "http:request",
  "name": "用户登录接口",
  "data": {
    "type": "http:request",
    "url": "{{api_base}}/api/v1/auth/login",
    "method": "post",
    "headers": {
      "Authorization": "Bearer {{token}}"
    },
    "body_type": "body",
    "content_type": "json",
    "body": "{\"username\": \"admin\", \"password\": \"{{password}}\"}",
    "timeout_ms": 30000
  }
}

核心配置参数 (Core Fields)

参数名 类型 默认值 说明
url string — 目标请求地址，全面支持 {{var}} 变量动态插值
method string get HTTP 方法（大小写不敏感）
headers object {} 请求头键值对映射表，支持环境变量注入
body_type string none 请求体格式：none / body (文本/JSON) / form-data / x-www-form-urlencoded / binary
content_type string json 内容类型提示：json / text / html / xml
timeout_ms number 30000 超时毫秒数 (支持 1000–300000ms)

HTTP 节点输出数据结构

{
  "success": true,
  "status": 200,
  "body": { "id": 1, "token": "eyJhbGciOi..." },
  "headers": { "content-type": "application/json" },
  "timing": { "connect_ms": 45, "total_ms": 150 }
}

HTTP Ingress 与 Webhook 模拟服务

MPE Flow 支持在工作流内直接启动轻量级内嵌 HTTP 服务端监听，无需启动独立的 Express/Nginx 即可完成 Webhook 触发、异步回调与接口 Mock 仿真验证。

http:ingress — HTTP 服务端监听节点

http:ingress 节点在指定端口上启动监听，负责捕获外部推送的 Webhook 请求或客户端调用。执行器与调试引擎会自动将其作为起始根节点优先触发。

uuid: ingress-1
type: http:ingress
name: 订单 Webhook 接收器
data:
  type: http:ingress
  port: 8080
  path: /api/v1/webhook/order
  method: post
  timeout_ms: 30000
参数名类型默认值说明
portnumber8080本地监听绑定的 TCP 端口
pathstring/匹配的 URL 路由路径（如 /api/webhook）
methodstringany期待的 HTTP 请求方法（get、post、put、delete、any）
timeout_msnumber30000等待接收请求的最大超时时间（毫秒）

Ingress 节点输出数据 (下游可直接引用)

  • {{request_body}} — 外部客户端发来的 JSON 或原始请求体文本。
  • {{headers}} — 请求头映射（如 x-hub-signature-256、authorization）。
  • {{query}} — URL Query 查询参数键值对。
  • {{connection_id}} — 本次 HTTP 连接上下文 ID（供下游 http:respond 关联回包）。

http:respond — HTTP 模拟响应节点

http:respond 节点与 http:ingress 节点配合使用，通过 connection_id 将自定义的状态码、响应头与响应体回写给外部客户端。

uuid: respond-1
type: http:respond
name: 确认回调成功
data:
  type: http:respond
  connection_id: "{{connection_id}}"
  status_code: 200
  headers:
    Content-Type: application/json
  body: '{"code": 0, "msg": "Webhook received successfully", "order_id": "{{order_id}}"}'

断言验证节点 (Assertion)

校验上游数据是否符合业务预期，生成包含实际值、期望值与判定耗时的结构化测试报告。

{
  "uuid": "assert-1",
  "type": "assertion",
  "name": "校验接口返回",
  "data": {
    "type": "assertion",
    "mode": "all",
    "assertions": [
      { "id": "a1", "description": "状态码为 200", "target": "$.status", "operator": "eq", "expected": 200 },
      { "id": "a2", "description": "包含业务数据", "target": "$.body.data", "operator": "exists" }
    ]
  }
}

断言操作符分类 (Assertion Operators)

类别 支持的操作符

类型校验type_is (类型为 string/number/boolean/array/object)
区间范围between (数值在区间内)

丰富插件扩展协议

更多应用层与存储协议（Redis、MySQL/PostgreSQL、MongoDB、Kafka、SMTP、gRPC、MCP 等）均以一键安装的轻量级侧边进程插件形式提供 — 详见下方插件开发章节或访问 插件市场。

可视化调试与断点控制

MPE Flow 内置全功能图形化交互调试器（同时支持 CLI 交互式单步调试）。可在任意节点挂起执行、实时查看/修改上下文变量、跳过不稳定节点或注入模拟产物。

断点标记

鼠标悬停在画布任意节点上，点击节点顶部的断点红点即可切换断点状态。开启调试运行后，执行器将在遇到断点节点前自动暂停并聚焦画布视口。

调试动作与全局快捷键

动作 快捷键 说明
继续执行 (Continue)F5 / 继续恢复流程执行，直至遇到下一个断点或整个流程执行完毕。
单步跳过 (Step Over)F10执行当前暂停节点并立即在下一个相连节点暂停。遇到子流程节点时，将在后台完整运行整个子流程并在父流程下一节点暂停。
单步步入 (Step Into)F11在子流程 (flow:sub) 节点暂停时按 F11 步入其内部，并在子流程的首个有效节点暂停。对常规协议节点行为同单步跳过。
单步步出 (Step Out)Shift + F11当在子流程内部暂停时，快速执行完当前子流程剩余全部节点，并暂停在父流程中该子流程节点的下一个后继节点。
跳过节点 (Skip Node)—忽略当前节点的实际网络/系统执行，指定下游输出端口分支（如 true / false）并可自定义注入模拟 output 数据。
执行到底 (Run to End)—临时忽略后续所有断点，直接以正常模式运行完毕。
终止调试 (Stop)—强制中止当前调试会话，生成截至当前暂停节点的阶段性调试报告。

子流程步入步出与调用栈追踪

面对多层嵌套子流程的复杂业务场景，MPE Flow 调试引擎原生支持嵌套调用栈帧 (DebugCallFrame) 与分层级单步穿透。

子流程精细化单步控制

当执行推进至子流程节点时：

  • 步入 (Step Into / F11)： 画布无缝下钻至子流程拓扑视图，顶部面包屑动态显示当前嵌套层级（如 主流程 > 鉴权子流程），并在子流程首个执行节点高亮闪烁暂停。
  • 步过 (Step Over / F10)： 将子流程作为黑盒原子步骤执行，直接在父流程后续节点恢复暂停，适合快速跳过已验证成熟的公共模块。
  • 步出 (Step Out / Shift+F11)： 当深入排查完子流程中的关键步骤后，一键执行完毕子流程剩余节点并返回父级上下文，无需逐节点敲击单步。

多层调试调用栈帧 (Call Stack)

右侧执行面板 - 堆栈中将动态呈现清晰的嵌套调用链路：

#0 根工作流 (订单主链路) → 子流程节点: 支付结算
  #1 支付结算 (Payment Pipeline) → 子流程节点: Token 刷新
    #2 Token 刷新 (OAuth2 Refresh) → HTTP 节点: /oauth/token [PAUSED 已暂停]

点击调用栈中的任意父级栈帧，画布视口与变量面板将即刻回溯切换至该层级的工作流视图与变量快照，支持在父子流程之间随时横向对照调试数据。

交互式流程切片执行与人机协同 (HITL)

MPE Flow 支持从庞大的工作流中框选局部子图或单节点按需独立触发执行，无需从 Entry 节点完整跑完全流程。

执行选中节点 (run_slice)

在画布上框选或多选目标节点，右键唤出上下文菜单并选择 执行选中节点：

  • 零入度根节点自动推导： 编译器自动分析选中节点集合，将集合内部入度为 0 的节点识别为局部执行根节点，即使切片中没有 Entry 节点也能正常运行。
  • 临时运行防污染： 切片执行产生的数据纯内存运转，不会持久化写入左侧历史执行记录列表，保持测试历史整洁干净。
  • 敏捷调优验证： 适合在下游节点修改脚本算法、数据提取表达式或断言规则后，单步即时复测，免受上游耗时数据库或限流接口困扰。

人机协同 (HITL) 动态交互卡片

在自动化流转过程中，协议节点或 AI 智能体可通过 ask_human 协议发起人工确认或补充输入：

  • 流程安全挂起： 遇到人机交互步骤时，执行流程自动挂起等待，并在右侧 执行面板 (ExecutionPanel) 中弹出结构化交互卡片。
  • 表单数据提交： 用户可在卡片中输入文本、选择分支策略或授权操作。提交后，数据自动作为该节点的输出注入上下文变量池，驱动下游继续推进。
  • 切片运行指示徽标： 执行中的切片具备醒目的状态徽章与一键中止控制。

生命周期全阶段调试与视图联动

MPE Flow 调试引擎支持贯穿 Setup → Main → Teardown 全生命周期的无缝断点调试。

画布阶段自动跟踪与视口聚焦

在单步步进 (F10/F11) 或恢复执行直至遇到 Setup/Teardown 中的断点节点时：

  • 画布视口将自动切换展示当前暂停节点所在的阶段，免除用户手动点击阶段标签栏。
  • 顶部多标签栏实时显示各阶段的单步调试状态（已完成、暂停中、等待执行）。
  • 若用户在暂停状态下主动切换到其他阶段，顶部会常驻显示「一键跳转回暂停节点所在阶段」的快捷横幅。
  • 在 Teardown 阶段调试时，右侧变量池可直接查看已注入的 Main 阶段完整报告变量快照 $report。

插件系统概述

插件用于扩展 MPE Flow 的协议节点生态。插件作为独立的侧边子进程（Sidecar Process）运行，通过标准输入输出 (stdio) 与宿主进行轻量级 JSON-RPC 2.0 通信（按行分隔，支持 LF 与 CRLF）。应用启动时宿主自动拉起插件完成 describe 握手，将其声明的节点动态注册到全局 NodeRegistry 中。插件节点在工作流编排、执行引擎与测试报告中与内置原生节点享有完全一致的一等公民体验。

插件安装目录

将包含 plugin.json 元数据清单的插件目录放入系统插件存放目录（默认位于 get_data_dir()/plugins；Windows 下位于 %APPDATA%/multi-protocol-flow-executor/plugins；可通过 MPE_PLUGIN_DIR 环境变量自定义覆盖）。宿主在启动时自动同步扫描：格式不合法的插件将被安全跳过，连续 3 次握手失败的插件将被临时隔离以保障宿主稳定性。

plugin.json 清单规范

配置项 说明
name插件唯一标识（遵循命名规范，通常与插件目录名一致）
version语义化版本号 (SemVer)
description插件功能中文/英文描述
min_host_version兼容的最低宿主版本限制
entry启动该插件的命令 command 与参数 args（原生支持 Python/Node 等解释型脚本作为插件直接运行）
env注入到插件子进程的环境变量键值对
permissions权限声明项
capabilities.streamingtrue 表示常驻守护进程；false 表示按需启动并在空闲 60 秒后自动回收
capabilities.single_node节点级能力：true 表示支持通过 mpe run-node 命令单节点测试连通性
locales / default_locale界面多语言支持声明，宿主通过 MPE_LOCALE 环境变量向插件下发当前语言

官方开源协议插件

官方插件仓库已开源提供丰富的协议插件：amqp (RabbitMQ)、db (SQLite/MySQL/PostgreSQL)、grpc、imap、kafka、mcp、mongo、mqtt、redis、smtp 等。可通过编译放入插件目录，或直接通过内置的 插件市场 一键安装。

SDK 与自定义插件开发

插件 SDK 与底层 Wire 通信协议契约统一托管在独立的开源公共仓库中：multi-protocol-flow/mpe-plugin-sdk。Rust SDK 提供一等公民的强类型支持，同时提供轻量级 Python 和 Node.js 插件脚手架。Wire 类型直接共享自 mpe-plugin-sdk::protocol，确保宿主与插件之间永远不会产生协议漂移。

开发流程

  1. 克隆或引用 SDK 仓库
  2. 实现 Plugin Trait（实现 describe 声明节点元数据 + execute 执行协议调用；可选实现 flow_ended 释放每轮执行资源）
  3. 编译为跨平台二进制或编写启动脚本
  4. 将输出目录放置在 plugins/ 插件目录中进行联调

注册中心契约规范

  • GET {base}/plugins 返回可用插件列表，每项包含各操作系统平台的打包资产 (zip) url 与可选的 sha256 校验和（宿主将严格校验哈希，杜绝篡改）。
  • 支持的操作系统平台键：windows-x64 | windows-arm64 | linux-x64 | linux-arm64 | macos-x64 | macos-arm64。
  • Zip 包根目录必须包含以插件同名的唯一顶层文件夹，内部放置 plugin.json 与所有相关依赖产物。

公共插件注册中心默认通过 GitHub Pages 静态托管 (multi-protocol-flow.github.io/mpe-plugin-registry)。在网站的 插件市场页面 也可直接浏览最新插件生态。
